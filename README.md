# Hypharness

画面と中継を Cloudflare に置き、タスクを手元のノードで実行するハーネス。全体の設計と段階は [docs/architecture.md](docs/architecture.md)、実装した構成の図は [docs/flow-write.md](docs/flow-write.md) にある。

## 構成

| 場所     | 役割                                                                                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/`   | Cloudflare Workers で動く画面と中継。パスキーでログインし、ノードのペアリング、タスクの待ち行列、実行権（期限45秒と世代番号）を持つ                                                                 |
| `node/`  | 手元で動くノード。中継に WebSocket で接続し、割り当てられたタスクをエージェントに bubblewrap の隔離環境で解かせる。候補の計測もここで行う                                                           |
| `agent/` | 進化対象のエージェント。計測では、コミットから取り出したこのディレクトリを隔離環境に読み取り専用で置いて動かす。原文保存・記憶・文脈の圧縮・子への委任を持つ。仕様は [agent/SPEC.md](agent/SPEC.md) |

## 使う

```sh
bun install
bun run dev        # 画面と中継を http://localhost:5173 で動かす
bun run node <セッション>  # ノードを起動する。別の URL に接続するときは bun run node <セッション> <URL>
bun run dashboard [ポート]   # エージェントのやり取りの図を http://127.0.0.1:4173 で見る（このマシンからだけ開ける）
bun run auto <セッション> <リポジトリ> <最終目的のファイル> <1日の予算ドル> [読み取り専用のディレクトリ...]  # RSI のループを自動で回す
```

初回はノードがコードを表示するので、画面にログインしてホームで入力する。トークンは `~/.hyph/node.json` に保存し、次回から自動で接続する。タスクは課題文と任意の判定コマンド（終了コード 0 で成功）からなる。ノードはセッションの稼働版のエージェントで課題文を解かせ、判定コマンドがあれば作業用ディレクトリで実行して成否を決める。セッションは「候補を測る」の命令で作り、基準版と予算の基準を持つものを指定する。タスクの出力は中継に送らず、`~/.hyph/logs/<タスク番号>-<世代>.log` に残し、エージェントを動かすたびに（実際のタスク・計測の試行・改善役・課題の生成役）、モデルの呼び出しをログの隣の `<ログ>.calls.jsonl` に1回ずつ残す。ダッシュボードはこの記録と計測のセッションを読んで、会話ごとの列と委任の矢印でやり取りを描き、一覧を2秒ごと、選んだ図を1秒ごとに読み直す。計測の試行の記録は、終わってセッションに移したら消す。中継に送るのは終了コード・成否・解いた版のコミットだけである。ノードの実行には bubblewrap（`bwrap`）と、ユーザーの systemd（`systemd-run --user`）が必要。隔離環境1つのメモリを 4GB、同時に動く隔離環境の合計を 10GB までに制限するために使う。

エージェントは課題をまたいで残す状態（記憶など）を、隔離環境の `/state` に置く。ノードではセッションごとの `~/.hyph/state/<セッション>` を渡し、判定付きのタスクの成否も置く。エージェントは次のタスクの初めに、使った記憶の評価をその成否で上下させる。計測では試行ごとに空のディレクトリを渡し、課題の間で答えが漏れないようにする。記憶の持ち越しの効果は `state-check` で測る。成績用課題を順に解かせて状態を貯め、その複製から検証用課題を測り、状態なしの検証用の計測と比べる。この計測は記憶ありの計測と同じく、オフライン RSI の比較には混ぜない。

ノードは実行中の作業領域を20秒ごとに暗号化して中継に送る。ノードが落ちて実行権が切れると、別のノードがそのチェックポイントから再開する。暗号の鍵は `~/.hyph/vault.key` にあり、最初のノードが作る。別のノードで再開できるようにするには、このファイルを各ノードの同じ場所に複製する。中継は鍵を持たない。中継は暗号化したデータを、内容の SHA-256 をキーにして R2 に置く。

## RSI のループを自動で回す

`bun run auto` は、指定したリポジトリの origin を `~/.hyph/repos/<セッション>` に複製して作業領域にし（利用者の作業ツリーには触れない。開発環境の設定は起動のたびに `nix print-dev-env` で作り直し、`~/.cargo/registry` を渡したときは `CARGO_HOME` とオフラインの指定を足す。課題を作る前に隔離環境で `cargo build` を試し、通らなければモデルを呼ばずに止める）、最終目的の保存、課題の用意（足りない分を `mine` で作る）を済ませてから、改良（`evolve` を6周）と採用（`promote`、上位3件を3回ずつ測り直す）を繰り返す。ループのたびに複製を origin の既定のブランチの最新に合わせるため、マージされた PR はノードのタスクにも入る。基準版が測り直したすべての回（3回）で解いた課題と、9回以上どの版も解けなかった課題は、候補の差を見分けられないため毎ループの最後に外し、次のループで同じ数を最新の履歴から作る。どの課題も解けないまま main が最も新しい課題のコミットから10コミット以上進んだときも、課題を外して最新の履歴から作り直し、基準版と予算の基準を測り直す。採用された版は、ノードが次のタスクから試験版として使い、成績が下回らなければ稼働版になる。1日の総予算は必須で、自己改善の区分の予算を使い切ると UTC の翌日まで待つ。下の各コマンドは、このループの段階を個別に動かすときに使う。hibana の最終目的は `goals/hibana.md` にある。

```sh
bun run auto hibana ~/ghq/github.com/mikan-919/hibana goals/hibana.md 5 ~/.cargo/registry
```

## 候補を測る

最終目的はセッションごとに変わるため、課題と予算の基準はセッション名ごとに `~/.hyph/sessions/<セッション>.sqlite` に分けて保存する。モデルの提供元は `PROVIDER` で切り替える。`deepinfra`（既定）は `.env` の `DEEPINFRA_API_KEY` を使い、既定のモデルは `deepseek-ai/DeepSeek-V4.1-Flash-1017`。`codex` は ChatGPT のサブスクリプションでサインインした OpenAI を使い、既定のモデルは `gpt-6-luna`。例: `PROVIDER=codex bun run node <セッション>`。予算の基準は解答役のモデルごとに持つため、切り替えた先のモデルで初めて測るときに決まる。候補（解答役・改善役）のモデルは `MODEL`・`REASONING` の環境変数でも選べる。課題の生成役と関連性の判定役は `GENERATOR_MODEL`・`GENERATOR_REASONING` で別に選べ、未設定なら候補と同じモデルを使う。候補と同じモデルでは、候補がときどき解けない正しい課題を作りにくい。OpenAI のサインインは `~/.hyph` で `bunx @earendil-works/pi-ai login openai` を実行して行う。

```sh
bun run measure <セッション> generate <最終目的のファイル> [検証用の数] [成績用の数]  # 課題を生成して選別する
bun run measure <セッション> review [件数]                                           # 課題を無作為に選んで表示する
bun run measure <セッション> run <コミット> [回数] [val|test|both]                      # 候補の成功率と費用を測る
bun run measure <セッション> evolve [周回数] [最初の基準版のコミット] [simple|explore]  # オフライン RSI を回す
bun run measure <セッション> promote [候補の数] [測り直す回数]  # 配る版（基準版）を決め、試験版にする
bun run measure <セッション> deploy <コミット>  # 指定したコミットを試験版にする
bun run measure <セッション> ideas [期数]  # 経済のループで記憶（方針の文章）を改善する
bun run measure <セッション> budget <ドル>  # 1期（1日）の総予算を決める
bun run measure <セッション> ledger  # 期ごとの予算・使用額・改善量を表示する
bun run measure <セッション> ideas-check [回数]  # 記憶ありとなしを成績用課題で比べる
bun run measure <セッション> harden [val|test] [生成する数]                            # 課題を敵対的に強化する
bun run measure <セッション> flag <課題の番号>                                         # 抽出確認で関係しない課題を外す
bun run measure <セッション> workspace <リポジトリ> <開発環境の設定> [読み取り専用のディレクトリ...]  # 課題をリポジトリの上に作る
bun run measure <セッション> pr [試行の番号]  # 成功した試行の差分からリポジトリに PR を作る（番号なしで候補を表示）
bun run measure <セッション> mine [検証用の数] [成績用の数] [差分の行数の上限]  # 作業領域のリポジトリの過去のコミットを種にして課題を作る
bun run measure <セッション> state-check <コミット> [回数]  # 成績用課題で貯めた状態（記憶）から検証用課題を測り、状態なしと比べる
bun run measure <セッション> proposals  # 改善役が出した固定部の変更の提案を表示する
bun run measure <セッション> approve|reject <提案の番号>  # 提案を承認して hypharness に PR を作るか、棄却する
```

`workspace` を設定したセッションでは、課題を `generate` のときのリポジトリの HEAD の上に作る。生成役は隔離環境のリポジトリの複製でシェルを使い、変更と隠しテストを作って提出し、解答役は同じコミットの中身で解く。hibana の場合は次のように設定する。開発環境の設定には、依存の取得済みの置き場を指す `CARGO_HOME` を足す（隔離環境にはネットワークがない）。

```sh
(cd ~/ghq/github.com/mikan-919/hibana && nix print-dev-env) > ~/.hyph/hibana.env.sh
echo "export CARGO_HOME=$HOME/.cargo CARGO_NET_OFFLINE=true" >> ~/.hyph/hibana.env.sh
bun run measure hibana workspace ~/ghq/github.com/mikan-919/hibana ~/.hyph/hibana.env.sh ~/.cargo/registry
bun run measure hibana generate <最終目的のファイル> 4 2
```

`mine` は、作業領域のリポジトリの過去のコミットを1件ずつ種にする。そのコミットの1つ前を課題のコミットにし、そのコミットの変更を当てた複製から、生成役に課題文と隠しテストだけを書かせる。変更そのものが模範解答になるため、ゼロから作らせるより少ない手順で課題ができる。種にするのは、既存の課題のコミットすべての祖先にあたるコミットだけで、文書だけの変更と、差分が上限（既定400行）を超える変更は使わない。生成役は同時に4つまで動かす。

`harden` は、基準版の解けた割合と失敗の記録を生成役に渡して新しい課題を作らせ、基準版に4回ずつ解かせて、解けた割合が20〜80%の課題だけを加える。課題を加えたときは、基準版が3回以上の計測ですべて解いた課題を外し、その分割の予算の基準を作り直す。

課題は、模範解答が判定を通る・空の解答では通らない・最終目的に関係する、の3つを満たすものだけを表に入れる。最初の計測の費用を予算の基準として記録し、以降は1課題あたり基準の2倍を上限にする。

`evolve` は1周ごとに、親候補を選び、親自身に `agent/` を直させ、門番（`agent/` の外の変更の禁止、隔離環境での型検査と `agent/` のテスト、自己編集の能力確認）を通った候補を1回測り、セッションの記録に残す。`explore` で並べて回す周回は、改善対象を周回ごとに先に決めてから並べる。基準版は変えない。`promote [候補の数] [測り直す回数]` は、記録の上位の候補を1回ずつ測り直し（基準版との対にした差が 0 以下になったら打ち切る）、検証用で基準版を確かに上回り、成績用で確かに下回らない候補を新しい基準版にする。比べるのは、解答役のモデル・推論の深さ（`MODEL`・`REASONING`）と課題の組が今と同じ計測だけで、設定を変えたり課題を足したりする前の計測は使わない。候補のコミットは `refs/hypharness/` に置き、ブランチと作業ツリーには触れない。

`explore` を指定すると、親の成功と失敗の応答から失敗の共通原因を生成役のモデルにまとめさせて改善役に渡し、改善対象（指示文・1つの機能・仕様・コード全体）を UCB1 で選び、変更を120行以内に制限する。仕様を選んだときは、改善役は先に `agent/SPEC.md` を直し、それに合わせてコードを直す。

門番を通った候補は、生成役のモデルが批評役として差分を読み、説明した改善に要らない変更を含むファイルを挙げる。そのファイルを親の版に戻した候補が門番を通れば、そちらを測る。改善役は固定部（`node/`・`src/`）の複製も読め、失敗の原因が固定部にあるときは変更を `META.patch` に書ける。固定部の変更は自動では採用せず、提案として残す。画面の「進化」か `approve` で承認すると、ノードが hypharness の既定のブランチから切ったブランチに当てて PR を作る。

`HYPH_TRIALS=relay` を付けて計測すると、試行を手元で解かずに、`~/.hyph/node.json` の中継の待ち行列に置き、接続中のノードに解かせる。試行の中身（課題・候補のコード・作業領域のリポジトリの中身と開発環境の設定）と結果（差分・モデルの呼び出しの記録）は `vault.key` で暗号化し、中継はハッシュと状態だけを持つ。作業領域の課題では、読み取り専用のディレクトリ（`~/.cargo/registry` など）が解くノードの同じパスに要る。既定は手元で解く。中継とペアリング済みのノードが要るためである。

試験配備では、ノードがタスクの25%を試験版で解く。判定付きのタスクで試験版と稼働版の結果が3件以上ずつ貯まり、試験版が確かに下回ったら、試験版を外して候補を不採用にし、基準版も稼働版へ戻す。試験版の判定付きの結果が10件に達して下回っていなければ、試験版を稼働版にする。記録はセッションの `deployments` 表に残る。

`ideas` は、worker（指示文・実行方針・技能の担当）が記憶に加える1行を出し、投資家が資本に比例して試す番を配る。稼働版で今の記憶と新しい記憶を検証用課題で5回ずつ測り、成功率が確かに上がったか、成功率を下げずに平均費用が2割以上下がったら採用する。採用された記憶は、ノードが実際のタスクを解くときにも課題文の前に置く。

費用はすべて、区分（目的遂行・局所改善・自己改善・検証）と期（UTC の日付）つきで記録する。`budget` で総予算を決めると、区分に配分し、直前の期に採用があった自己改善・局所改善の配分を増やす。自己改善と局所改善は、その期の予算を使い切ると止まる。内訳はノードが中継に送り、画面の「資源配分」で見られる。

## 配備する

画面と中継は Cloudflare Workers に配備する。チェックポイントを置く R2 のバケットは、初回だけ先に作る。

```sh
bunx cf r2 buckets create --name hypharness-checkpoints
bun run deploy
```

ノードは `bun run node <セッション> <配備先の URL>` で配備先とペアリングする。
