# hypharness

最上位の目的を与えると、複数のエージェントが目標・タスク・知識・担当領域・エージェント構成を自分たちで変えながら作業し、検証済みの成果物を作業ディレクトリに残すエージェントハーネス（モデル呼び出し、ツール実行、状態管理を受け持つ実行基盤）です。共有状態の管理（DeLM）と各エージェントの文脈管理（CLM）を分けて実装しています。

## 使い方

`auth.json` に ChatGPT の認証情報がある状態で、目的を渡して起動します。モデルは `OPENAI_MODEL`（既定値 `gpt-6-sol`）、推論の強さは `REASONING`（既定値 `medium`）で指定します。Web 検索を使わせる場合は、Parallel の API キーを環境変数 `PARALLEL_API_KEY` に設定します（`.env.example` を `.env` に写して書き込むと、プロジェクト直下で実行したときに Bun が自動で読み込みます）。設定すると、エージェントは `web_search` ツールで Parallel Search API（`https://api.parallel.ai/v1/search`）に検索語を送り、関連順の URL と抜粋を受け取ります。キーがない起動では、このツールはモデルに渡す道具の一覧から外れます。

```bash
bun install
bun run start 'CSVを集計するCLIを書き、テストを通す' --constraints 'TypeScriptのみ' --allow-shell --calls 80
bun run start --allow-shell --calls 160   # 同じ状態から再開する
bun run start status                     # 目標・エージェント・使用量を表示する
```

状態は `.hyph/state.sqlite`、成果物は `.hyph/workspace/`、各エージェントの文脈の写しは `.hyph/contexts/<agent>.md` に置かれます。別の場所を使う場合は `--dir` を指定します。目的は最初の起動時に固定され、別の目的で同じ状態を開くとエラーになります。

| オプション | 意味 |
| --- | --- |
| `--mode single\|fixed\|dynamic` | 組織の形。single は1体、fixed は lead・worker・reviewer の3体で増減なし、dynamic はエージェントが生成・休眠を判断する（既定値） |
| `--calls N` | モデル呼び出し回数の累計上限（既定値 200）。状態に保存され、再開時に指定すると上書きされる。再開して続けるには、使用済みの回数より大きい値を指定する |
| `--agents N` / `--concurrency N` | エージェント数と同時実行数の上限 |
| `--allow-shell` | `shell` ツールを許可する。許可は起動ごとに判断し、指定しない起動では拒否される |
| `--rounds N` | スケジューラーの巡回回数の上限 |
| `--check 'cmd'` | 終了後に作業ディレクトリで実行する検査コマンド。終了コードを結果に含める |

## 比較実験

```bash
bun run bench 'ToDo管理のCLIを書く' --calls 60 --allow-shell --check 'bun test'
```

同じ目的・モデル・呼び出し上限で single、fixed、dynamic を別々の状態で順に実行し、完了状態、最上位目標が独立検証されたか、検査コマンドの終了コード、モデル呼び出し数、入出力トークン数、キャッシュ読み取りトークン数、最大入力文字数、経過時間、エージェント数、組織変更数を `.hyph/bench-<時刻>/report.json` に書きます。モデルの応答は実行ごとに変わるため、結果も実行ごとに変わります。

## LoCoMo-Plus ベンチマーク

[LoCoMo-Plus](https://github.com/xjtuleeyf/Locomo-Plus)（長期にわたる会話の記憶を測る評価。LoCoMo の5分類の質問に、会話の前のほうにある暗黙の手がかりを後の発言に結び付けられるかを問う Cognitive 分類を加えたもの）で、ハーネスと単発のモデル呼び出しを比較します。

```bash
bun run src/index.ts locomo --arms direct,single,dynamic --per-category 2 --calls 40
bun run src/index.ts locomo --arms direct --categories Cognitive,adversarial --per-category 10
bun run src/index.ts locomo --out .hyph/locomo-1234   # 中断した実行を同じ出力先で続ける
```

| オプション | 意味 |
| --- | --- |
| `--arms` | 比較する方式。`direct` は参照実装と同じく会話全体と質問を1回の呼び出しで渡す。`single`・`fixed`・`dynamic` はハーネスをその組織で1問ごとに実行する（既定値 `direct,dynamic`） |
| `--per-category N` | 分類ごとの問題数。`all` で全2,387問（既定値 2） |
| `--categories` | 対象の分類（multi-hop, temporal, common-sense, single-hop, adversarial, Cognitive） |
| `--seed N` | 問題の選び方を決める乱数の種。同じ種なら全方式が同じ問題を解く（既定値 1） |
| `--calls N` | ハーネス方式の1問あたりの呼び出し上限（既定値 40） |
| `--concurrency N` | `direct` の同時実行数（既定値 2） |
| `--judge-model ID` | 採点に使うモデル（既定値は `OPENAI_MODEL`） |
| `--out DIR` | 出力先（既定値 `.hyph/locomo-<時刻>`） |

データは参照実装のリポジトリから固定したコミットの `locomo10.json` と `locomo_plus.json` を取得し、`.hyph/locomo-data/` に保存します。リポジトリにライセンスの記載がないため、データはこのリポジトリに含めていません。問題の組み立て（会話の整形、根拠の文、手がかりと発言の挿入位置）と採点（分類ごとの判定文、correct=1・partial=0.5・wrong=0、判定結果の読み取り）は参照実装を移植しています。参照実装と同じく、時刻が重なって会話を組み立てられない Cognitive の33問は、モデルを呼ばずに `(no input_prompt)` として採点します。

ハーネス方式では、会話を1回で読める大きさ（3,000文字以下）のファイルに分けて作業ディレクトリの `conversation/` に置き、目的として指示と質問を渡します。エージェントは `file_search` と `file_read` で必要な箇所を探し、答えを `answer.txt` に書きます。各問題のセッションは `<出力先>/<方式>/<問題ID>/` に残り、ダッシュボードで経過を確認できます。

出力先には次のファイルができます。予測と採点は1問ごとに追記され、同じ出力先で再実行すると済んだ問題を飛ばします。モデル提供元のエラーは予測や採点として記録せず、3回続くと中断します。

- `predictions.jsonl`: 方式・問題ごとの予測、終わり方（`answered`、ハーネスの `done`・`budget` など）、呼び出し回数とトークン数、時間
- `judgments.jsonl`: 判定ラベル、理由、点数、判定結果を文字列の一致で読み取ったかどうか
- `report.json`: データの出典とハッシュ値、問題 ID の一覧、方式ごとの平均点・分類別の平均点・使用量・採点にかかった使用量

論文は主要な結果の採点に使ったモデルを明記していません（人手との一致を調べた実験では gemini-2.5-flash、リポジトリの使用例では gpt-4o-mini）。そのため、別のモデルで採点した点数とは直接比較できません。参照実装は予測で temperature 0.3、採点で 0 を指定しますが、ChatGPT でサインインしている場合、pi-ai は temperature を送りません。

## ダッシュボード

ハーネスの操作画面です。実行の開始・再開・停止と、進行状況・成果物・テレメトリの確認をブラウザで行えます。

```bash
bun run dashboard                 # http://127.0.0.1:4321/ で開く
bun run dashboard --dir .hyph --port 4321
```

- **新規実行**: 最上位目的、制約、セッション名、組織（single・fixed・dynamic、または3方式を比較する bench）、呼び出し上限、エージェント数と同時実行数の上限、終了後の検査コマンド、シェルの許可を指定して起動します。状態は `--dir`（既定値 `.hyph`）の下の `<セッション名>/` に保存されます。
- **実行の操作**: 実行中のセッションは停止でき、停止中のセッションは呼び出し上限（累計）・検査コマンド・シェルの許可を指定し直して再開できます。停止はハーネスのプロセスを終了させますが、ツール呼び出しの記録と実行中エピソードの再開により、再開時に作業を重複させません。実行の出力は画面に表示され、セッションの `run.log` にも追記されます。ダッシュボードを終了すると、そこから起動した実行も停止します。
- **表示**: `--dir` の下にあるすべての `state.sqlite` をセッションとして切り替えて表示します。状態ファイルは読み取り専用で開き、数秒ごとに再取得します。
  - 最上位目的と、呼び出し回数・入力トークン（キャッシュ分を含む）・キャッシュ読み取りの割合・最大入力文字数などの集計
  - エージェントごとの状態・役割・生成元・実行中のタスク・使用量。行を選ぶと、作業記憶とその履歴、実行中の文脈、過去のエピソードの内容を表示する
  - 作業ディレクトリのファイル一覧と内容（成果物）
  - 呼び出しごとの入力文字数と入力トークンのグラフ、および呼び出しの記録の表
  - タスク、目標、知識と領域、イベントログ

画面は shadcn/ui（コピーして使う React の UI 部品集）と Tailwind CSS で作られ、Bun の HTML インポートで配信されます。Tailwind の変換は `bunfig.toml` で読み込む `bun-plugin-tailwind` が行います。

このサーバーはシェルを許可した実行を起動できるため、`127.0.0.1` でのみ接続を受け付けます。加えて、Host ヘッダーが自身でない要求（DNS リバインディング: 外部のドメイン名をローカルのアドレスに向けてブラウザ経由で接続させる攻撃）と、Origin ヘッダーが自身でない、または JSON でない変更要求（CSRF: 別のサイトからブラウザに要求を送らせる攻撃）を拒否します。利用者の認証はないため、外部に公開しないでください。コマンドラインから同じセッションを同時に実行した場合は検出できません。

## 仕組み

**実行の循環。** スケジューラーは巡回ごとに、待ち作業がない未完了の目標を見つけると、その目標の所有者に「次の手を決める」タスク（steer）を割り当てます。所有者は自分で作業する、タスクや下位目標を作る、目標を修正・破棄する、`goal_complete` で提出する、のいずれかを選びます。最初の作業も同じ規則で lead に割り当てられ、計画の手順は固定されていません。最上位目標 G0 の内容は変更できません。

**検証。** 作業タスクの完了と目標の提出は、提出者以外のエージェントによる検証タスクを生みます。合格するまで完了扱いになりません。dynamic で検証できるエージェントがいない場合は、休眠中のエージェントを起こすか `verifier` を生成します。single では自己検証として `verified_by` に本人が記録されます。知識は常に未検証の仮説として登録され、`knowledge_verify` による検証で verified か rejected になります。

**知識。** 知識は Gist（1行）、Summary（短い説明）、Raw（原資料）の3段と出典を持ちます。検索結果は Gist だけを返し、必要なときに `knowledge_get` で展開します。担当領域（domain）は知識への参照だけを持つため、分割・統合・移譲で知識本体は複製も削除もされません。領域の変更は管理者（steward）だけが行えます。

**文脈（CLM）。** 各エージェントは、タスクをまたいで残る作業記憶と、実行中のタスクの文脈（live context）を持ちます。作業記憶は `memory_write` で書き換え、上限（既定値 6000 文字）を超えると拒否されます。旧版は履歴に残り、`memory_restore` で戻せます。実行中の文脈は `context_outline` と `context_edit` で、読み終えた大きな出力などを短い注記に置き換えられ、次の生成から反映されます。置き換え前の文脈は `episode_history` に残ります。他のエージェントの文脈は `context_read` で一部だけ読めますが、編集はできません。他者の動きは自動では入力に挿入されず、`news` で前回の確認以降の差分を要約で取得します。

**入力の大きさ。** システムプロンプトには目的・制約・役割・規則だけを入れ、時刻や件数を入れないため、プロンプトキャッシュ（同じ先頭部分の計算結果をプロバイダーが再利用する仕組み）が効きます。各タスクは作業記憶とタスク説明だけから始まり、1タスクの手数（既定値 16）とツール出力の長さ（既定値 4000 文字）に上限があるため、作業量が増えても1回の入力は一定の範囲に収まります。

**継続と整合性。** すべての状態は SQLite に置かれ、各手番の後に文脈を保存します。タスクの取得は条件付き更新で1体だけが成功し、取得には期限（lease）があり、期限切れは再び取得可能になります。ツール呼び出しは (エピソード, 呼び出しID) ごとに結果を記録し、再開時に記録済みの呼び出しは再実行しません。起動時には前のプロセスが残した取得期限を無効とみなし、実行中だったエピソードをそのまま再開します。モデル呼び出しは5分（環境変数 `MODEL_TIMEOUT_MS` で変更可）で打ち切り、モデルエラーとして扱います。同じタスクで3回続けてモデルエラーが起きると、タスクを手放します。すべてのエピソードが失敗する巡回が3回続くと（利用上限や認証の失敗など）、予算を使い切る前に `error` で停止します。ファイル操作は作業ディレクトリの外（シンボリックリンク経由を含む）を拒否します。

## 開発

```bash
bun run check   # 型検査
bun test        # 擬似プロバイダーによる結合テスト（外部モデルを呼ばない）
```

テストは、目的だけからの計画・実行・独立検証・完了、検証のためだけに組織が変わること、停止後の再開でツールの副作用が重複しないこと、作業量を増やしても入力が増えないこと、作業ディレクトリ外へのパスの拒否を確認します。

ホストは1プロセスで動かす前提です。複数プロセスで同じ状態を開くと、実行中エピソードの再開が衝突します。
