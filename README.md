# Hypharness

画面と中継を Cloudflare に置き、タスクを手元のノードで実行するハーネス。全体の設計と段階は [docs/architecture.md](docs/architecture.md) にある。

## 構成

| 場所     | 役割                                                                                                                                      |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `src/`   | Cloudflare Workers で動く画面と中継。パスキーでログインし、ノードのペアリング、タスクの待ち行列、実行権（期限45秒と世代番号）を持つ       |
| `node/`  | 手元で動くノード。中継に WebSocket で接続し、割り当てられたタスクをエージェントに bubblewrap の隔離環境で解かせる。候補の計測もここで行う |
| `agent/` | 進化対象のエージェント。計測では、コミットから取り出したこのディレクトリを隔離環境に読み取り専用で置いて動かす                            |

## 使う

```sh
bun install
bun run dev        # 画面と中継を http://localhost:5173 で動かす
bun run node <セッション>  # ノードを起動する。別の URL に接続するときは bun run node <セッション> <URL>
```

初回はノードがコードを表示するので、画面にログインしてホームで入力する。トークンは `~/.hyph/node.json` に保存し、次回から自動で接続する。タスクは課題文と任意の判定コマンド（終了コード 0 で成功）からなる。ノードはセッションの稼働版のエージェントで課題文を解かせ、判定コマンドがあれば作業用ディレクトリで実行して成否を決める。セッションは「候補を測る」の命令で作り、基準版と予算の基準を持つものを指定する。タスクの出力は中継に送らず、`~/.hyph/logs/<タスク番号>-<世代>.log` に残す。中継に送るのは終了コード・成否・解いた版のコミットだけである。ノードの実行には bubblewrap（`bwrap`）が必要。

## 候補を測る

最終目的はセッションごとに変わるため、課題と予算の基準はセッション名ごとに `~/.hyph/sessions/<セッション>.sqlite` に分けて保存する。候補（解答役・改善役）のモデルは `MODEL`・`REASONING` の環境変数で選ぶ。課題の生成役と関連性の判定役は `GENERATOR_MODEL`・`GENERATOR_REASONING` で別に選べ、未設定なら候補と同じモデルを使う。候補と同じモデルでは、候補がときどき解けない正しい課題を作りにくい。サインインは `~/.hyph` で `bunx @earendil-works/pi-ai login openai` を実行して行う。

```sh
bun run measure <セッション> generate <最終目的のファイル> [検証用の数] [成績用の数]  # 課題を生成して選別する
bun run measure <セッション> review [件数]                                           # 課題を無作為に選んで表示する
bun run measure <セッション> run <コミット> [回数] [val|test]                         # 候補の成功率と費用を測る
bun run measure <セッション> evolve [周回数] [最初の基準版のコミット] [simple|explore]  # オフライン RSI を回す
bun run measure <セッション> promote [候補の数] [測り直す回数]  # 配る版（基準版）を決め、試験版にする
bun run measure <セッション> deploy <コミット>  # 指定したコミットを試験版にする
bun run measure <セッション> harden [val|test] [生成する数]                            # 課題を敵対的に強化する
bun run measure <セッション> flag <課題の番号>                                         # 抽出確認で関係しない課題を外す
```

`harden` は、基準版の解けた割合と失敗の記録を生成役に渡して新しい課題を作らせ、基準版に4回ずつ解かせて、解けた割合が20〜80%の課題だけを加える。課題を加えたときは、基準版が3回以上の計測ですべて解いた課題を外し、その分割の予算の基準を作り直す。

課題は、模範解答が判定を通る・空の解答では通らない・最終目的に関係する、の3つを満たすものだけを表に入れる。最初の計測の費用を予算の基準として記録し、以降は1課題あたり基準の2倍を上限にする。

`evolve` は1周ごとに、親候補を選び、親自身に `agent/` を直させ、門番（`agent/` の外の変更の禁止、隔離環境での型検査と `agent/` のテスト、自己編集の能力確認）を通った候補を1回測り、セッションの記録に残す。基準版は変えない。`promote [候補の数] [測り直す回数]` は、記録の上位の候補を測り直し、検証用で基準版を確かに上回り、成績用で確かに下回らない候補を新しい基準版にする。候補のコミットは `refs/hypharness/` に置き、ブランチと作業ツリーには触れない。

`explore` を指定すると、親の成功と失敗の応答から失敗の共通原因を生成役のモデルにまとめさせて改善役に渡し、改善対象（指示文・1つの機能・コード全体）を UCB1 で選び、変更を120行以内に制限する。

試験配備では、ノードがタスクの25%を試験版で解く。判定付きのタスクで試験版と稼働版の結果が3件以上ずつ貯まり、試験版が確かに下回ったら、試験版を外して候補を不採用にし、基準版も稼働版へ戻す。試験版の判定付きの結果が10件に達して下回っていなければ、試験版を稼働版にする。記録はセッションの `deployments` 表に残る。
