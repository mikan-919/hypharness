# 設計

hypharness は、手元の GPU 1枚で、複数の研究エージェントに LLM のアーキテクチャと学習法の研究を自動で進めさせるハーネスである。最終的には、研究エージェント自身のコードを改善する（RSI: Recursive Self-Improvement。エージェントが自分のコードを書き換え、計測で改善を確かめてから採用する仕組み）。

旧版（Cloudflare の中継、ノード、モデルに作らせた課題による RSI）は、課題を保つための仕組みが増え続け、改善を確認できなかったため作り直した。

## 1. 原則

1. 指標は機械が計算する1つの数値にする。研究の指標は val bpb（検証データ1バイトあたりの交差エントロピーをビットで表したもの。トークナイザーによらず比べられる）とする。
2. 採点の仕組みは、エージェントが書き換えられない場所に置く。データ・予算・評価は固定部（`research/prepare.py`）にあり、エージェントには読み取り専用で見せる。
3. ばらつきより小さい差では採用しない。基準の学習を繰り返して標準偏差を測り、最良を2標準偏差より大きく下回ったときだけ最良を更新する。
4. 予算は時間ではなく量で決める。GPU は Windows の画面と共有されていて、他の処理が VRAM と計算を取ると同じ学習が4倍以上遅くなることがあった。学習に使うバイト数（`TOKEN_BUDGET`）で予算を決めれば、混み具合で変わるのは時間だけになる。
5. 研究エージェントの間に指揮役を置かない。協調は DeLM（Decentralized Language Models、[arXiv:2606.10662](https://arxiv.org/abs/2606.10662)）にならい、共有の文脈だけで行う。

## 2. 構成

| 部品 | 場所 | 役割 |
| --- | --- | --- |
| ハーネス | `main.go`、`lab.go` | 研究エージェントの起動、GPU の待ち行列、実験の記録、最良の管理 |
| モデルの呼び出し | `openai.go` | Sign in with ChatGPT で受け取ったトークンで OpenAI の Responses API を呼ぶ。pi-ai（MIT）の openai-chatgpt を移植した |
| 共有の文脈 | `shared.go` | DeLM 式の追記だけのログ |
| 隔離環境 | `sandbox.go` | bubblewrap と systemd-run。システムは読み取り専用、ネットワークなし、環境変数は消す。学習のときだけ WSL の GPU を見せる |
| 研究エージェント | `agent/` | 将来の自己改善の対象。Go の静的なバイナリにして隔離環境に置く |
| 研究の固定部 | `research/prepare.py` | データ、予算、評価 |
| 研究の対象 | `research/train.py` | 基準の学習スクリプト（バイト単位の GPT） |

言語は Go にした。研究エージェント1体のメモリは数 MB〜数十 MB で済み、ビルドは1秒程度なので、将来の自己改善で候補を試すたびにビルドしても負担にならない。学習スクリプトだけは Python と PyTorch で書く。

研究エージェントは隔離環境の中から Unix ソケット `/hyph.sock` だけで外とやり取りする。トークンとモデルの選択はハーネスが持ち、エージェントには見せない。

| エンドポイント | 中身 |
| --- | --- |
| `POST /model` | Responses API の呼び出し。ハーネスがモデル・推論の深さ・`store: false` を付ける |
| `GET /context` | 共有の文脈のうち、前回読んだ後に増えた項目 |
| `POST /claim`、`/release`、`/fact`、`/fail` | 共有の文脈への追記 |
| `POST /train` | 申告した仮説について `/work/train.py` を GPU で学習させる |

## 3. 研究の1周

1. ハーネスは研究エージェントの作業用ディレクトリを最良の `train.py` だけにして起動する。
2. エージェントは共有の文脈を読み、仮説を1つ `claim` で申告し、`train.py` を変え、CPU で短く動作を確かめる。申告には比較元（出発点にした `train.py` の実験の番号）を付ける。
3. `train` で GPU の待ち行列に入る。ハーネスは1本ずつ学習させ、出力の最後の `val_bpb:` の行を読む。
4. ハーネスは結果を実験ノート（`runs.jsonl`）に残し、最良を2標準偏差より大きく下回れば最良を更新する。結果は、比較元を2標準偏差より大きく下回れば `fact`、そうでなければ `fail` として共有の文脈に書き、申告を閉じる。全体の最良と比べないのは、並行して最良が更新されたときに、比較元に対して効いた変更を否定された仮説として残さないためである（10体の試運転で、学習率のスケジュールの変更が比較元を 0.063 改善したのに `fail` と記録された）。
5. エージェントは発見を `fact` か `fail` に書いて終わる。ハーネスは新しい文脈で起動し直す。前の研究が閉じなかった申告は `release` で手放す。

## 4. 共有の文脈（DeLM）

DeLM は、指揮役を置かずに複数のエージェントを協調させる手法である。全員が追記だけをするログを共有し、各自が課題を申告して進める。論文では2〜4体のコーディングと文書の質問応答で、単体のエージェントを最大17.5ポイント上回った。ここでは次の部分を取り入れた。

- 項目は `claim`（申告）、`fact`（根拠のある発見）、`fail`（否定された仮説）、`release`（手放した申告）の4種類。既存の項目は書き換えず、誤りは新しい `fail` で指摘する。
- 1体が同時に持てる未完了の申告は1つまで。学習は申告がないと始められない。
- 読むと前回からの差分だけが返る。新しい研究は文脈が空なので、初めから読む。

開放的な研究で10体を協調させて効くかは、論文からは分からない。段階3の計測で確かめる。

## 5. 段階

### 段階1: 研究のスワーム（実装済み）

サインイン、モデルの呼び出し、隔離環境での学習、GPU の待ち行列、ばらつきの計測、共有の文脈、複数体の研究エージェント。

### 段階2: 評価の分離

今は `train.py` が `prepare.report` を呼び、その出力をハーネスが読む。検証データは学習と同じ隔離環境に見えるので、エージェントは検証データで学習することも、評価を書き換えることもできる。規則で禁じているだけである。自己改善で最適化の圧力をかける前に、次のように分ける。

- 学習の隔離環境には学習データだけを見せ、重みを保存させる。
- 別の隔離環境で、固定部の評価が重みを読んで val bpb を出す。

### 段階3: 研究エージェントの自己改善

研究エージェントの候補（`agent/` の1コミット）を、「決まった予算（GPU の時間とモデルの呼び出し）で、決まった出発点の `train.py` から val bpb をどれだけ下げたか」で比べる。1回の評価が研究を丸ごと1回分なので、費用もばらつきも大きい。段階1の記録で、1回の研究の改善量のばらつきを測ってから、比べるのに要る回数を決める。共有の文脈あり・なし、体数の違いもこの計測で比べる。

### 段階4: 研究課題を増やす

バイト単位の言語モデル以外の課題（別のデータ、別の指標）を `research/` と同じ形で足す。1つの課題に過剰に適合した研究エージェントを採用しないためである。

## 6. 未決事項

- 最良は1回の計測の値なので、たまたま低く出た値が残りうる。今は採用を厳しくする方向なので測り直さない。
- 新しい研究は共有の文脈を初めから読む。項目が増えて文脈を圧迫するようになったら、古い項目の要約を作る。
- モデルの呼び出しの予算を持たない。ChatGPT のサブスクリプションの利用上限（10体の `gpt-6.2-sol` で約1.5時間）に当たったら、10分ごとに試し直して戻るのを待つ。上限の戻る時刻は応答に含まれない。

## 7. 旧版から引き継いだ知見

- 隔離環境: bubblewrap で、システムを読み取り専用、作業用ディレクトリだけを書き込み可にし、ネットワークを含む名前空間を分け、環境変数を消す。bubblewrap はメモリを制限しないので、systemd の scope に入れ、1つあたりと合計に上限を付ける（上限なしで動かしたプログラムがメモリを取り尽くし、PC ごと落ちたことがある）。
- ばらつきより小さい差で採用しない。
- 推論の過程は保存させず、暗号化して返させて次の呼び出しで送り返す（`store: false` と `reasoning.encrypted_content`）。
