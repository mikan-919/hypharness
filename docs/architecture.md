# ハーネス全体の設計

この文書は、目標とする構成図（メインハーネス・オフライン RSI・分散配備基盤）を、実装できる段階に分けたものである。段階ごとに、作るもの、作らないもの、完了条件を定める。各段階の成否は、段階0bで作る計測で数値として判断する。

既存のコード（`runner/`、`src/`）はすべて作り直す。引き継ぐのは「5. 引き継ぐ知見」に挙げた設計だけである。

用語:

- RSI（Recursive Self-Improvement）: ハーネスが自分のコードや指示文を変更し、計測で改善を確かめてから採用する仕組み。オンラインは実行中のエージェントが自分の方針を直すもの、オフラインはハーネス全体の版を作り直すもの。
- 候補: ハーネスの1つの版。hypharness リポジトリの1コミットで表す。
- 基準版: 現在採用されている候補。図の「現行の検証済みハーネス」。
- 進化用課題: 候補の性能を測るための、答えを機械で判定できる課題。人が用意せず、最終目的から生成役のエージェントが作る。
- ノード: 利用者の端末で動くデーモン。エージェントと実験を隔離環境で実行する。
- 中継: Cloudflare Workers と Durable Object（1つの識別子に対して1つだけ動き、内部に SQLite を持つ Cloudflare の実行単位）で動くサービス。画面とノードを仲介し、登録・実行権・履歴を持つ。

## 1. 原則

1. 計測できないものは作らない。各段階は、段階0bの計測で前後を比べられる形で入れる。
2. 採点の仕組みは候補から書き換えられない場所に置く。評価器・課題の正解・予算の管理は「固定部」とし、候補が変更できるのは「進化対象」だけにする。
3. 雑音より小さい差では採用しない。採用の判断には、段階0bで測ったばらつきを使う。
4. 処理はノードで行い、中継は仲介と状態の記録だけを行う。モデルの認証情報、作業領域、実行記録の本文はノードの外に出さない。中継に置くのは、識別子・状態・数値・ハッシュだけにする。

固定部と進化対象の境界:

| 区分     | 含むもの                                                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 固定部   | 中継、ノードのデーモン、モデル呼び出しの中継（予算と認証情報を持つ）、評価器、課題の生成役と関連性の判定役、進化用課題と正解、候補の系統の記録、採否の判定 |
| 進化対象 | エージェント本体（行動ループ、記憶、文脈選択、作業文脈、ツール）と、それが持つ指示文                                                                       |

リポジトリでは、進化対象を1つのディレクトリにまとめ、候補が変更できる範囲をディレクトリ単位で判定できるようにする。

図の「改善機構自体を修正」（META）は固定部の変更にあたる。自動では採用せず、利用者が画面で承認したときだけ反映する。

## 2. 全体構成（図の③）

mikan-919/oriel と同じく、画面と中継をサーバーレスに置き、処理をローカルのノードで行う。

| 部品   | 動く場所                            | 役割                                                                                                     |
| ------ | ----------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 画面   | Cloudflare Workers                  | 管理・監視・承認。課題の抽出確認、META の承認                                                            |
| 中継   | Cloudflare Workers + Durable Object | ノード・エージェント・タスクの登録、タスクの割り当て、実行権の管理、確定チェックポイントと実行履歴の記録 |
| ノード | 利用者の端末（Bun）                 | 中継との常時接続、隔離環境（bubblewrap）での実行、モデル呼び出しの中継、作業領域と記憶の保存             |

図の要素との対応:

| 図の要素                                 | この設計での実装                                                                                                |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Node・Agent・Task Registry、複製管理状態 | 中継の Durable Object の SQLite。Durable Object は識別子ごとに1つだけ動くため、管理状態の合意に Raft を使わない |
| Scheduler / Reconciler                   | 中継が、空いているノードにタスクを割り当てる。期限切れの実行権を見つけたら、タスクを待ち行列に戻す              |
| 実行権管理（世代番号・排他制御）         | 実行権は WebSocket 接続に結び付け、期限（oriel は45秒）と世代番号を持たせる。古い世代からの報告は中継が拒否する |
| Git                                      | 候補のコードと系統。ノードから利用者のリポジトリへ push する                                                    |
| CAS / Snapshot                           | 作業領域を内容のハッシュで保存する。保存先はノードのローカルとし、複数ノードでの共有は段階6で決める             |
| Agent State                              | 記憶・目的・進捗・作業文脈の SQLite ファイル。チェックポイント時に複製を作る                                    |
| 確定チェックポイント                     | 版（コミット）・状態のハッシュ・作業領域のハッシュの組。中継に記録する                                          |
| 復旧                                     | 実行権が切れたタスクを別のノードに割り当て、確定チェックポイントから再開する（段階6）                           |

oriel との違い: oriel のデーモンは Rust で、Codex を実行する。hypharness は Bun で書き、モデルは pi-ai（`@earendil-works/pi-ai`）を通して呼ぶ。

## 3. 段階

### 段階0a: 中継とノードの骨格

作るもの:

- 中継: ノードの登録（パスキーで認証した利用者の画面からペアリングする）、タスクの待ち行列、実行権の発行と期限切れの回収、世代番号による古い報告の拒否、実行履歴の保存（保持期間と件数の上限を持つ）。
- ノード: 中継への常時接続と再接続、実行権の受け取り、隔離環境でのタスク実行、結果の報告。
- 画面: ペアリング、ノードの一覧、タスクと実行履歴の表示。

完了条件:

- ペアリングしたノードが、画面から入れたタスクを受け取り、結果を報告できる。
- 実行中にノードを強制終了すると、期限の後にタスクが待ち行列に戻ることを、テストで確かめている。
- 古い世代の実行権からの報告が拒否されることを、テストで確かめている。

### 段階0b: 計測の土台

作るもの:

- 進化用課題の表。1課題は「課題文」「隔離環境に置くファイル」「判定コマンド」「模範解答」で持つ。判定コマンドが終了コード0で終わったら成功とする。課題は検証用（探索中に使う）と成績用（非公開。採否の最終判断だけに使う）に分ける。
- 課題の生成役。最終目的の文章から課題を作る。作った課題は次の3つをすべて満たすときだけ表に入れる。
  - 模範解答が判定コマンドを通る（隔離環境で実行して確かめる）
  - 空の解答が判定コマンドを通らない
  - 関連性の判定役（生成役とは別の呼び出し）が、最終目的に関係すると判定する
- 成績用課題は、検証用とは別の呼び出しで生成し、改善役には課題文も結果も渡さない。
- 生成した課題の一部を画面で抽出確認できるようにする。課題・解答・判定を同系統のモデルが作るため、最終目的からのずれを人が見つける経路として残す。
- モデル呼び出しの中継（ノード内）。候補はこの中継を通してだけモデルを呼ぶ。中継は認証情報を持ち、入出力トークン数と費用を候補・課題ごとに記録し、計算予算を超えた呼び出しを拒否する。候補の隔離環境からは、中継の Unix ソケット以外へのネットワークを遮断する。
- 実行記録。候補・課題・試行ごとに、成否・費用・実行履歴（会話とツールの入出力）をノードの SQLite に残す。図の Meta-Harness のログにあたる。
- 1つのコミットを全課題で測る処理（`bun run measure <セッション> run <コミット>`）。まず1台のノードで行う。課題と試行の組を中継のタスクとしてノードに分配し、成否と費用を中継に送る処理は、複数のノードで測る必要が出たときに足す。
- 最終目的はセッションごとに変わる。課題の表・予算の基準・計測の記録は、セッションごとの SQLite（`~/.hyph/sessions/<セッション>.sqlite`）に分け、1つのセッションでは最終目的を変えない。

計算予算: 基準版で1回測ったときの費用を記録し、以降の計測の予算の基準にする。予算は課題ごとに分け、1課題の上限を「基準の1課題あたりの費用の2倍」とする。全体で1つの上限にすると、並列で後に回った課題だけが予算切れになり、課題の順番で成否が変わるためである。2倍は、ばらつきで基準版自身が予算切れにならないための余裕で、段階1の記録を見て見直す。

完了条件:

- 最終目的の文章だけから課題を生成し、上の3条件で選別した課題の表ができる。模範解答が通らない課題と、空の解答で通る課題が除かれることを、テストで確かめている。
- 基準版を同じ課題で5回測り、成功率の平均と標準偏差を出せる。1回の費用を記録し、予算の基準にしている。
- 判定コマンドや正解のファイルを、候補の中から読めないし書けないことを、テストで確かめている。
- 予算を超えた呼び出しが拒否されることを、テストで確かめている。

### 段階1: オフライン RSI の最小ループ

作るもの:

- 候補の系統の記録（DGM の系統樹）。候補ごとにコミット・親・変更の説明・成績を持つ。
- 改善役のエージェント。親候補自身（DGM・SICA と同じく自分のコードを直す）を、親の agent/ の複製と検証用課題での実行記録を置いた作業用ディレクトリで動かす。変更は一時的なインデックスで agent/ だけを親のツリーに重ねてコミットし、`refs/hypharness/` に置く。利用者の作業ツリーとブランチには触れない。
- 門番。agent/ の外を変えたコミットを止め、隔離環境の中で型検査と agent/ のテストを行い、さらに自己編集の能力確認（その候補を改善役として動かし、agent/ に決められたファイルを作れるか）を通った候補だけを測る。候補のコードはホストで実行しない。
- 採否。比べる相手は親ではなく基準版とする。親が基準版より低いとき、親を上回っただけの候補を基準版にしないためである。検証用課題で基準版との差が、基準版を繰り返し測った成功率の標準偏差の2倍を超えた候補だけを成績用課題で測り、成績用課題でも基準版を下回らなければ基準版にする。それ以外は不採用にせず、親の候補として系統に残す。
- 親の選び方は、検証用の成功率に0.1を足した値で重み付けして確率で選ぶ。

完了条件:

- 1周（親の選択→変更→門番→計測→採否）が人の操作なしで終わり、結果が系統の記録に残る。
- 型検査を壊す変更、テストを壊す変更、進化対象の外を書き換えようとする変更が、それぞれ不採用になることを確かめている。

### 段階2a: 課題の敵対的強化

段階0bの課題は基準版がすべて解き、候補の差が出ない。2bの探索方針を比べるにも差の出る課題が要るため、2aを先に行う。

作るもの（`bun run measure <セッション> harden [val|test] [数]`）:

- 生成役に、その分割の課題と基準版の解けた割合、失敗したときの応答を渡し、新しい課題を作らせる。成績用の課題は成績用の情報だけから強化し、改善役が見る検証用の情報と混ぜない。
- 生成役が課題を1つ提出するたびに選別し、その結果（判定の出力、関係なしの判定、基準版の解けた割合）をツールの結果として返す。生成役はそれを見て3回まで出し直せる。除外の理由を返さないと、生成役は判定コマンドの誤り（例: `bun test` が拾わない名前のテスト）を知らないまま同じ誤りを繰り返すためである。段階0bの最初の生成も同じ方式で行う。
- 選別の3条件を通った課題を基準版に4回ずつ解かせ、解けた割合が20〜80%に入る課題だけを加える。生成役の成績は、帯に入った課題の数とする。解けた割合が0%の課題は、差を測れず、意味のない難問へ寄る原因になるため加えない。
- 課題を1つ以上加えたときだけ、基準版が3回以上の計測ですべて解いた課題を外す。課題が変わると1回の計測の費用も変わるため、その分割の予算の基準を消し、次の計測で作り直す。
- 課題の集合は強化のたびに変わるため、親と子は常にその時点の同じ課題で測り直して比べる。
- 抽出確認は `review` で表示し、関係しない課題を `flag` で外す。外した割合を強化の記録に残す。

完了条件:

- 強化の前後で、課題の解けた割合の分布と、抽出確認で関係なしとされた課題の割合を記録している。

### 段階2b: 探索の方針

作るもの:

- 弱点の抽出。成功と失敗の実行記録を並べ、共通する失敗原因を文章にまとめる（Self-Harness、ModularRSI の対比分析）。改善役への入力に加える。
- 改善対象の選択。指示文（GEPA）、機能単位の修正（ModularRSI）、仕様（SpecForge）、実装コード（SICA/DGM）のどれを変えるかを UCB1（試行回数と過去の成績から、次に試す選択肢を決める方式。AIDE² が使う）で選ぶ。
- 変更量の上限と、未探索の箇所を優先する重み（RRSI）。

完了条件:

- 同じ計算予算で、段階1の単純な方式と段階2bの方式を比べ、採用された候補の成績を記録している。段階2bが上回らなければ、段階2bの仕組みは入れない。

### 段階3: 試験配備と復旧

作るもの:

- 版の固定。ノードは、採用済みの特定のコミットからエージェントを起動する。
- 試験配備。新しい基準版を目的遂行タスクの一部だけで動かし、旧版と成果・費用を比べる。
- 復帰。試験配備で旧版を下回ったら、旧版へ戻し、その候補を系統の記録で不採用にする。

完了条件:

- 意図的に性能を下げた候補を試験配備し、自動で旧版へ戻ることを確かめている。

### 段階4: メインハーネス（図の①）

①の各要素は、段階1〜3のループに改善させるか、人が実装して同じ計測を通す。どちらの場合も、段階0bの計測で上がったものだけを残す。最初の基準版は、「5. 引き継ぐ知見」の範囲で最小に作る。候補を次に挙げる。

- 原文保存（LCM）: 会話・観測・実行履歴を追記だけで残し、要約からいつでも原文へ戻れるようにする。
- 共有記憶と自己記憶（DeLM）: Gist・Summary・Raw の3段で持ち、Summary は原文からの引用で根拠を示す。
- 作業文脈（CLM）: モデルが作業文脈の追加・置換・削除・再配置を提案し、原文の保護と参照の維持を確かめてから反映する。
- 接頭辞キャッシュとトークン予算（TokenPilot）: 固定部分を先頭に置いて変えず、変動部分はその後に置く。文脈の編集はまとめて反映し、キャッシュを壊す回数を減らす。中継の記録でキャッシュの利用率を比べる。
- 文脈選択（VISTA ほか）: 作業記憶をブロック単位で持ち、トークン量・新しさ・参照履歴をモデルに見せる。
- 参照関係グラフ: エントリー間の参照（タスク・因果・依存）を表で持ち、想起の並べ替えに使う。
- 意味検索: 埋め込みによる検索を全文検索と併用する。
- 重複の検出と統合: 共有記憶の似たエントリーをまとめる。

完了条件: 項目ごとに、段階0bの計測で前後の成功率と費用を記録している。

### 段階4b: 経済のループをオンライン RSI にする

DeLM 型の分担（目的の分解とタスクの取り合い）に、資本と投資による配分を組み合わせた経済のループを作り、図の① E として使う。対応は次のとおり。

| 図の要素               | 経済のループでの対応                                                               |
| ---------------------- | ---------------------------------------------------------------------------------- |
| 改善仮説を生成         | worker のアイデア。対象を指示文・実行方針・技能に限る                              |
| 隔離環境で局所検証     | アイデアを適用した worker と適用しない worker で、検証用課題の一部を解かせて比べる |
| 費用を含めて改善したか | この比較の結果（成功率の差と費用の差）で採点する。LLM による採点は使わない         |
| 自己方針に反映・共有   | 採用したアイデアを自己記憶に入れ、改善案・適用条件・根拠を共有記憶と実行記録に残す |
| 局所改善予算           | worker の資本と投資家の投資                                                        |

アイデアが変えられるのは自己記憶（指示文・方針・技能）だけで、コードは変えない。コードの変更は段階1のオフライン RSI だけが行う。

完了条件: 採用されたアイデアを持つ worker と持たない worker の成功率と費用を、成績用課題で比べて記録している。

### 段階5: 資源配分

作るもの:

- 予算を、目的遂行・局所改善・自己改善（段階1〜2）・検証（段階0bの計測）に分ける。
- 自己改善の予算は、直近の採用候補による改善量に応じて増減させる。局所改善の予算は、段階4bで採用されたアイデアの改善量に応じて投資家が配分する。

完了条件: 期ごとの予算の内訳と、それに対する改善量を画面で見られる。

### 段階6: チェックポイントと別ノードでの復旧

開始する条件: 段階1が完了したとき（失うと困る長い実行が生じるため）。

作るもの:

- ノードが一定の区切りで、作業領域・記憶・作業文脈を保存し、確定チェックポイントを中継に記録する。
- 実行権が切れたタスクを別のノードに割り当て、確定チェックポイントの状態から再開する。
- 作業領域と記憶をノード間で受け渡す保存先（R2 などのオブジェクトストレージか、ノード間の直接転送か）は、開始時に決める。

完了条件: 実行中のノードを強制終了し、別のノードが確定チェックポイントから再開して、同じ課題を完了できる。

## 5. 引き継ぐ知見

既存のコードは削除するが、次の設計は作り直しでも使う。

- 隔離環境: bubblewrap で、システムを読み取り専用、作業用ディレクトリだけを書き込み可にし、ネットワークを含む名前空間を分け、環境変数を消す。
- 全文検索: 日本語は単語の区切りがないため、SQLite FTS5 の trigram（3文字単位）で索引する。
- 要約の検証: Summary の各行に原文からの引用を持たせ、引用が原文に含まれるかを機械で確かめる。
- mikan-919/oriel から: 実行権を接続に結び付けて期限と世代番号で古い保持者を排除する方式、実行履歴の保持期間と件数の上限、中継に本文や認証情報を置かない方針。
