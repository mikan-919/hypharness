# ハーネス全体の設計

この文書は、目標とする構成図（メインハーネス・オフライン RSI・分散配備基盤）を、実装できる段階に分けたものである。段階ごとに、作るもの、作らないもの、完了条件を定める。各段階の成否は、段階0で作る計測で数値として判断する。

用語:

- RSI（Recursive Self-Improvement）: ハーネスが自分のコードや指示文を変更し、計測で改善を確かめてから採用する仕組み。オンラインは実行中のエージェントが自分の方針を直すもの、オフラインはハーネス全体の版を作り直すもの。
- 候補: ハーネスの1つの版。hypharness リポジトリの1コミットで表す。
- 基準版: 現在採用されている候補。図の「現行の検証済みハーネス」。
- 進化用課題: 候補の性能を測るための、答えを機械で判定できる課題。人が用意せず、最終目的から生成役のエージェントが作る。

## 1. 原則

1. 計測できないものは作らない。各段階は、段階0の計測で前後を比べられる形で入れる。
2. 採点の仕組みは候補から書き換えられない場所に置く。評価器・課題の正解・予算の管理は「固定部」とし、候補が変更できるのは「進化対象」だけにする。
3. 雑音より小さい差では採用しない。採用の判断には、段階0で測ったばらつきを使う。
4. 機械1台で回る間は分散化しない（③は最後）。

固定部と進化対象の境界:

| 区分 | 含むもの |
|---|---|
| 固定部 | 評価器、課題の生成役と関連性の判定役、進化用課題と正解、候補の系統の記録、モデル呼び出しの中継（予算と認証情報を持つ）、採否の判定 |
| 進化対象 | `runner/agent.ts`、`runner/context.ts`、`runner/loop.ts`、`runner/tools.ts`、`runner/economy.ts` と、それらが持つ指示文 |

図の「改善機構自体を修正」（META）は固定部の変更にあたる。自動では採用せず、利用者が画面で承認したときだけ反映する。

## 3. 段階

### 段階0: 計測の土台

作るもの:

- 進化用課題の表。1課題は「課題文」「隔離環境に置くファイル」「判定コマンド」「模範解答」で持つ。判定コマンドが終了コード0で終わったら成功とする。課題は検証用（探索中に使う）と成績用（非公開。採否の最終判断だけに使う）に分ける。
- 課題の生成役。最終目的の文章から課題を作る。作った課題は次の3つをすべて満たすときだけ表に入れる。
  - 模範解答が判定コマンドを通る（隔離環境で実行して確かめる）
  - 空の解答が判定コマンドを通らない
  - 関連性の判定役（生成役とは別の呼び出し）が、最終目的に関係すると判定する
- 成績用課題は、検証用とは別の呼び出しで生成し、改善役には課題文も結果も渡さない。
- 生成した課題の一部を画面で抽出確認できるようにする。課題・解答・判定を同系統のモデルが作るため、最終目的からのずれを人が見つける経路として残す。
- モデル呼び出しの中継。候補はこの中継を通してだけモデルを呼ぶ。中継は認証情報を持ち、入出力トークン数と費用を候補・課題ごとに記録し、固定の計算予算を超えた呼び出しを拒否する。候補の隔離環境からは、中継の Unix ソケット以外へのネットワークを遮断する。
- 実行記録。候補・課題・試行ごとに、成否・費用・実行履歴（会話とツールの入出力）を SQLite に残す。図の Meta-Harness のログにあたる。
- 1つのコミットを全課題で測るコマンド。

計算予算: 基準版で1回測ったときの費用を記録し、以降の1回の計測の予算はその値とする。

完了条件:

- 最終目的の文章だけから課題を生成し、上の3条件で選別した課題の表ができる。模範解答が通らない課題と、空の解答で通る課題が除かれることをテストで確かめている。
- 基準版を同じ課題で5回測り、成功率の平均と標準偏差を出せる。1回の費用を記録し、予算の基準にしている。
- 判定コマンドや正解のファイルを、候補の中から読めないし書けないことを、テストで確かめている。
- 予算を超えた呼び出しが拒否されることを、テストで確かめている。

### 段階1: オフライン RSI の最小ループ

作るもの:

- 候補の系統の記録（DGM の系統樹）。候補ごとにコミット・親・変更の説明・成績を持つ。
- 改善役のエージェント。親候補のコードの複製と、親の失敗した実行記録を受け取り、進化対象のファイルを変更して差分を出す。
- 門番。`bun run typecheck` と `bun test` を通り、さらに自己編集の能力確認（その候補を改善役として動かし、決められた小さな変更を差分として出せるか）を通った候補だけを測る。
- 採否。検証用課題で親より上がり、その差が段階0のばらつきを超えた候補だけを、成績用課題で測る。成績用課題でも親を下回らなければ基準版にする。
- 親の選び方は、成績上位から確率で選ぶ単純な方式にする。

完了条件:

- 1周（親の選択→変更→門番→計測→採否）が人の操作なしで終わり、結果が系統の記録に残る。
- 型検査を壊す変更、テストを壊す変更、評価器を書き換えようとする変更が、それぞれ不採用になることを確かめている。

### 段階2: 探索の方針

作るもの:

- 弱点の抽出。成功と失敗の実行記録を並べ、共通する失敗原因を文章にまとめる（Self-Harness、ModularRSI の対比分析）。改善役への入力に加える。
- 改善対象の選択。指示文（GEPA）、機能単位の修正（ModularRSI）、実装コード（SICA/DGM）のどれを変えるかを UCB1（試行回数と過去の成績から、次に試す選択肢を決める方式）で選ぶ。
- 変更量の上限と、未探索の箇所を優先する重み（RRSI）。
- 課題の敵対的強化。生成役に、基準版が失敗した課題と実行記録を渡し、新しい課題を作らせる。生成役の評価は「選別の3条件を満たし、基準版の解けた割合が20〜80%に入る課題の数」とする。解けた割合が0%の課題は、差を測れず、意味のない難問へ寄る原因になるため数えない。基準版が安定して解くようになった課題は検証用から外す。
- 課題の集合は期によって変わるため、親と子は常にその時点の同じ課題で測り直して比べる。測った結果はコミットと課題の組ごとに残し、同じ組は測り直さない。

完了条件:

- 同じ計算予算で、段階1の単純な方式と段階2の方式を比べ、採用された候補の成績を記録している。段階2が上回らなければ、段階2の仕組みは入れない。
- 敵対的強化の前後で、課題の解けた割合の分布と、抽出確認で関係なしとされた課題の割合を記録している。

### 段階3: 試験配備と復旧

作るもの:

- 版の固定。ランナーは、採用済みの特定のコミットから起動する。
- 試験配備。新しい基準版を経済のループの一部の worker だけで動かし、旧版と成果・費用を比べる。
- 復帰。試験配備で旧版を下回ったら、旧版へ戻し、その候補を系統の記録で不採用にする。

完了条件:

- 意図的に性能を下げた候補を試験配備し、自動で旧版へ戻ることを確かめている。

### 段階4: メインハーネスの改善

①の未実装部分は、段階1〜3のループに改善させるか、人が実装して同じ計測を通す。どちらの場合も、段階0の計測で上がったものだけを残す。候補を次に挙げる。

- 接頭辞キャッシュ: 固定の指示文を先頭に置き、想起した記憶はその後のメッセージへ移す。中継の記録でキャッシュの利用率を比べる。
- トークン予算: 作業文脈が上限を超えたとき、`rewrite_context` を求めるか、古い手を Gist に置き換える。
- 参照関係グラフ: エントリー間の参照（タスク・因果・依存）を表で持ち、想起の並べ替えに使う。
- 意味検索: 埋め込みによる検索を FTS5 と併用する。
- 重複の検出と統合: 共有記憶の似たエントリーをまとめる。

完了条件: 項目ごとに、段階0の計測で前後の成功率と費用を記録している。

### 段階4b: 経済のループをオンライン RSI にする

経済のループ（`runner/economy.ts`、`runner/loop.ts`）を、図の① E として組み直す。対応は次のとおり。

| 図の要素 | 経済のループでの対応 |
|---|---|
| 改善仮説を生成 | worker のアイデア。対象を指示文・実行方針・技能に限る |
| 隔離環境で局所検証 | アイデアを適用した worker と適用しない worker で、検証用課題の一部を解かせて比べる |
| 費用を含めて改善したか | 市場の LLM 採点を、この比較の結果（成功率の差と費用の差）に置き換える |
| 自己方針に反映・共有 | 採用したアイデアを自己記憶に入れ、改善案・適用条件・根拠を共有記憶と実行記録に残す |
| 局所改善予算 | 会社・worker の資本と投資家の投資 |

アイデアが変えられるのは自己記憶（指示文・方針・技能）だけで、コードは変えない。コードの変更は段階1のオフライン RSI だけが行う。

完了条件: 採用されたアイデアを持つ worker と持たない worker の成功率と費用を、成績用課題で比べて記録している。

### 段階5: 資源配分

作るもの:

- 経済のループの予算を、目的遂行・局所改善・自己改善（段階1〜2）・検証（段階0の計測）に分ける。
- 自己改善の予算は、直近の採用候補による改善量に応じて増減させる。局所改善の予算は、段階4bで採用されたアイデアの改善量に応じて投資家が配分する。

完了条件: 期ごとの予算の内訳と、それに対する改善量を画面で見られる。

### 段階6: 分散配備（③）

開始する条件: 1回の計測（段階0）が機械1台で12時間を超える状態が続いたとき。それまでは作らない。

作るもの（開始時に詳細を決める）: ノードと課題の登録、実験の割り当て、実行権の排他（世代番号）、作業領域の保存と復元。合意（Raft など）は、管理ノードを複数にする必要が出たときに入れる。

## 4. 未決事項

- 敵対的強化で、解けた割合の帯（20〜80%）が妥当か。段階2の記録を見て調整する。
