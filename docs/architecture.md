# 仕組み

常駐プロセスはチャット、記憶市場、仕事の枠を並行して動かします。利用者の状態は `.hyph/main/state.sqlite` に保存し、LoCoMo、`rsi` は測定用の別の状態を使います。SQLite は WAL（書き込みと読み取りを両立させる記録方式）で開きます。

| ファイル | 役割 |
| --- | --- |
| `src/index.ts` | 常駐起動、目的設定、測定用コマンド |
| `src/dashboard/server.ts` | ローカルの画面とチャット・目的設定の受付 |
| `src/resident.ts` | 常駐用の初期状態と目的変更 |
| `src/resident-memory.ts` | 文の保存、埋め込み、距離と管轄への割り当て |
| `src/resident-market.ts` | 記憶の探索、評価、資本と信用、担当の再編、成果の記録 |
| `src/scheduler.ts` | 常駐用の仕事の枠と、測定用の巡回方式 |
| `src/agent.ts`, `src/tools.ts`, `src/triggers.ts` | エピソード、道具、仕事と検証の発火条件 |
| `src/web-fetch.ts` | 名前解決と転送先を検証したページ取得 |
| `src/mcp.ts`, `src/sandbox.ts` | MCP サーバーへの接続と、シェル・標準入出力サーバーの隔離環境 |
| `src/locomo.ts`, `scripts/rsi*.ts` | 測定と自己改善 |

## 目的と仕事

常駐用の G0 はホストが保持し、仕事を割り当てません。利用者の目的設定は `meta` と G0 を更新し、`order_changed` を記録します。開いている下位目標ごとに所有者への再検討タスクを追加します。エピソードの開始時に目的を取り込むため、実行途中のエピソードは中断しません。

仕事の枠は実行中の担当を追跡し、空いた枠から次のタスクを取得します。提出された目標は別の担当による検証を経て完了します。常駐中は仕事がなくても終了せず、発言、目的変更、タスクの追加や市場の発見による通知を待ちます。通知漏れと再試行のため、長い間隔の確認も行います。取得期限、モデル呼び出しとツールの結果は保存され、再起動時に実行中のエピソードを引き継ぎます。

## 記憶と市場

`knowledge` に記憶の原文と出典、`memory_vectors` に埋め込み、`domain_knowledge` に管轄との対応を保存します。埋め込みは `Xenova/multilingual-e5-small` の passage 接頭辞、目的との比較には query 接頭辞を使います。テストでは埋め込み関数を差し替えます。市場の発見、担当の信用・資本・戦略、利用者の反応、乱数の状態も保存します。

記憶の候補は、直近6件の窓にある発言を除いた記憶から作ります。目的との距離と記憶同士の距離を使い、遠い組み合わせも選びます。記憶が2件未満の場合、利用者の目的と利用できる記憶から仕事を提案し、根拠を補った発見としては扱いません。担当内の距離分布から候補を選び、評価役には対象と順位の隣接候補を渡します。評価された発見は応答用の材料となり、仕事が必要と評価された案は目標になります。応答に渡した発見と利用者の次の発言を評価し、信用と資本を更新します。

担当は投資を受けた際に、分布から作られた分割候補と統合の申し入れを検討できます。分割時は新しい担当へ記憶を移し、統合時は申し入れ先の受諾を必要とします。目標の完了時は成果と出典を記憶し、G0 の直下の目標だけチャットに報告します。

## 現状の制約

担当の譲渡は申し入れ先の受諾を必要とします。信用と資本は担当に属し、複数の管轄を持つ担当の値は同期します。既存データに管轄ごとに異なる値がある場合、移行前の値を保存し、譲渡先がもともと持っていた管轄の値を優先します。過去の譲渡記録が足りない場合は元の担当の値を特定できません。休眠した担当は分割先や低資本の戦略の交代先として再利用します。投資家役と評価役も信用と資本に基づいて休眠中の戦略を変異させ、交代します。市場の候補は記憶の組み合わせを比較するため、記憶数が増えると処理量が増えます。ツールが追加した知識は埋め込みを計算して最も近い管轄に登録します。

画面はローカルアドレスで受け付け、変更要求の Host と Origin を検査します。`web_fetch` は接続前と転送ごとに名前解決の結果を検査し、検査したアドレスに接続します。シェルは bubblewrap 内で実行し、利用には `--allow-shell` が必要です。

## MCP サーバー

`mcp.json` は状態ファイルと同じディレクトリに置きます。形式は `{"mcpServers":{"名前":{"command":"bun","args":["/workspace/server.js"],"env":{"KEY":"値"}},"別名":{"type":"http","url":"http://127.0.0.1:8080/mcp","headers":{"X-Key":"値"}}}}` です。設定がなければ接続しません。起動時に各サーバーへ接続してツール一覧を取得し、失敗したサーバーの理由を記録して除きます。切断後は次の呼び出し前に再接続します。

標準入出力のサーバーはシェルと共通の bubblewrap の設定で起動し、環境変数は設定の `env` だけを渡します。HTTP の URL はホストが指定した接続先として扱い、プライベートアドレスも拒否しません。ツール名には `mcp__サーバー名__ツール名` を使い、取得した説明と入力スキーマ（引数の形を表す定義）をモデルに渡します。成功した結果の全文は `mcp:サーバー名/ツール名` を出典とする未検証の知識に保存し、モデルへの出力は既存の上限で切ります。接続と通信には `@modelcontextprotocol/sdk` を使います。
